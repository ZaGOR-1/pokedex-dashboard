# Pokédex Analytics

Навчальний проєкт із дисципліни **«Компонентно-орієнтоване програмування»**.

**Лабораторна робота №3. Заочна форма. Варіант №6: Pokédex.**

Мета роботи: створити контрольовану форму пошуку й фільтрації та винести затримку вводу і завантаження даних у власні хуки. Застосунок продовжує роботи №1 та №2.

## Що працює

- Завантаження 20 Pokémon із PokeAPI.
- Таблиця з ID, назвою, типами, HP, атакою та захистом.
- Сортування за ID, назвою та HP за зростанням і спаданням. Для цього потрібно натиснути заголовок стовпця.
- Чотири KPI: загальна кількість записів API, кількість Pokémon у вибірці, унікальних типів і Pokémon із двома типами.
- Контрольована форма з трьома полями: назва Pokémon, тип і мінімальний HP. Значення зберігаються у стані React Hook Form, кожне поле отримує `value` та `onChange` через `Controller`.
- Пошук частини назви без урахування регістру та пробілів навколо. Назва застосовується після паузи 400 мс, тип і HP одразу.
- HP приймає лише невід’ємні цілі числа в межах точних цілих JavaScript. Порожнє поле означає відсутність обмеження. Записи без відомого HP не проходять заданий поріг.
- Кнопка «Скинути фільтри» одразу очищує назву й HP та повертає всі типи. Тема, лічильник і вибране сортування зберігаються.
- Таблиця та три KPI вибірки змінюються разом після фільтрації. Загальна кількість записів API показується окремо.
- Повідомлення про завантаження, помилку та відсутність даних. Після помилки можна повторити запит кнопкою.
- Лічильник місць у команді від 0 до 6, світла й темна тема.
- Адаптивна сторінка. На вузькому екрані таблиця прокручується у своїй області.

## Технології

React 19, TypeScript, Vite, React Hook Form та CSS. Для тестування використано Vitest і React Testing Library, для перевірки коду та форматування: ESLint і Prettier.

## Встановлення та запуск

Потрібні Node.js `^22.22.2`, `^24.15.0` або `>=26.0.0` та npm.

```bash
git clone https://github.com/ZaGOR-1/pokedex-dashboard.git
cd pokedex-dashboard
npm ci
npm run dev
```

Відкрийте адресу, яку покаже Vite в терміналі, зазвичай `http://localhost:5173`. Для завантаження даних потрібен доступ до PokeAPI.

Збірка та перегляд готової версії:

```bash
npm run build
npm run preview
```

## Перевірки

```bash
npm run lint
npm run typecheck
npm run format:check
npm run test
npm run build
```

Тести перевіряють поля форми, затримку вводу, завантаження даних, скасування запитів, застарілі відповіді, помилки, сортування, фільтри, KPI, лічильник і тему. У тестах використовуються підготовлені відповіді API, тому доступ до мережі для них не потрібний.

Для ручної перевірки введіть `saur`, виберіть `poison` і вкажіть HP `60`. Після затримки мають залишитися Ivysaur і Venusaur. KPI вибірки: 2 Pokémon, 2 типи, 2 Pokémon із двома типами. Задайте HP `999`, щоб побачити порожній результат, потім скиньте фільтри. Склад реальної відповіді залежить від PokeAPI.

## Власні хуки та рух даних

`useDebounce<T>(value, delay)` зберігає відкладене значення у `useState`. Ефект запускає таймер і прибирає його при зміні значення, затримки або демонтуванні компонента. Для назви використано 400 мс. Очищення назви та скидання форми застосовуються одразу.

`useFetch<T, P>(request, params)` приймає функцію завантаження `(signal, params)` і параметри. Він повертає `data`, `loading`, `error` та `refetch`. При зміні функції, параметрів або ручному повторі попередній запит скасовується через `AbortController`. Пізні відповіді скасованих запитів ігноруються. Функція запиту й об’єкт параметрів мають зберігати посилання між рендерами, наприклад через `useCallback` і `useMemo`, якщо вони створюються в компоненті.

На цьому етапі запит фіксований: `useFetch` викликає наявний `loadPokemon`, а HTTP-логіка залишається у `PokeApiClient`. Завантажується список `/pokemon?limit=20&offset=0`, потім характеристики цих записів групами до чотирьох запитів. Повтор виконується кнопкою після помилки.

Форма передає значення селектору `filterPokemon`: назву після debounce, тип і HP без затримки. Селектор працює з отриманими даними `useFetch`. Відфільтрований масив надходить до таблиці та підрахунку KPI. Фільтрація й сортування не змінюють вихідний масив. Під час введення, скидання та сортування нові HTTP-запити не виконуються.

## Організація коду

- `src/app/`: головний компонент, який збирає сторінку.
- `src/components/`: форма, таблиця, KPI, лічильник, тема та контейнер, який поєднує хуки й селектори.
- `src/hooks/`: перевикористовувані `useDebounce` і `useFetch`, які містять побічні ефекти.
- `src/domain/pokemon/`: модель Pokémon, фільтрація, сортування та підрахунок показників.
- `src/application/pokemon/`: опис результату завантаження.
- `src/infrastructure/pokeapi/`: запити до PokeAPI, перевірка й перетворення відповідей.
- `tests/`: налаштування та дані для тестів. Тести компонентів лежать поруч із відповідними файлами в `src/`.

## Обмеження

- Завантажується лише перша сторінка з 20 записів. Пошук за назвою, тип, HP і сортування працюють лише в цій вибірці. Область пошуку вказана над формою. Пошуку всієї бази та перемикання сторінок поки немає.
- PokeAPI не надає серверних параметрів для довільного пошуку частини назви, типу та HP у списку `/pokemon`. Тому форма фільтрує вже отримані записи локально. Див. [документацію API](https://pokeapi.co/docs/v2).
- Загальний KPI враховує записи API, включно з формами Pokémon. Решта KPI описують відфільтровані записи таблиці. Кількість унікальних типів може перевищувати кількість Pokémon, бо один запис має кілька типів.
- У фільтрі залишено 18 стандартних типів. Інші типи з коректними назвами показуються в таблиці без окремого варіанта у фільтрі.
- Якщо не вдається завантажити хоча б один запис, сторінка показує помилку. Стан віджетів не зберігається після перезавантаження.

Джерело даних: [PokeAPI](https://pokeapi.co/). Pokémon належать їхнім правовласникам. Проєкт призначений для навчання.
